# D-message 第一期设计：在线规则与 Trace

**状态**　设计评审稿，待实现。  
**基线**　D-message `310b45a`，本机 Magpie `0.1.4520`。产品界面沿用英语。  
**评审目标**　确定用户如何定义规则、一次真实调用会发生什么、事后能从 Trace 证明什么，以及哪些接入方式能兑现这些行为。

**阅读顺序**　产品审阅可先看第 1 节的决定表、第 3.4 节的完整规则和第 7 节的 Trace；接入、故障和交付评审集中在第 5、6、9 节。

## 1. 功能边界与审阅决定

用户在一条真实请求或回应中选中字段，建立规则，在旧 Trace 上试跑，启用后处理后续流量。用户回到 Trace，应能回答四个问题：哪条规则生效、改了什么、请求有没有转发、客户端最终收到了什么协议结果。

| 规则 | D-message 对上游的操作 | 对原客户端的结果 |
|---|---|---|
| Request / Rewrite | 转发一次修改后的请求 | 得到本次调用的一个结果 |
| Request / Block | 在转发前终止，上游调用数为零 | 得到一个规则错误 |
| Response / Rewrite | 上游已经响应，在交付前改写回应 | 得到一个修改后的结果 |
| Response / Block | 保留上游已响应的事实，丢弃其正文 | 得到一个规则错误 |

“一个结果”按**一条入站请求**计算。SSE 可以有多个事件，但只能形成一份客户端结果。D-message 在线执行规则不会自行重发模型请求。Magpie 内部的供应商切换，以及客户端收到错误后主动重试，分别由各自的组件管理。

**本期交付**包括 Rules 管理、历史试跑、在线执行、Trace 审计，以及已有 Repeater 打开来源快照的兼容。手动暂停等待放行、故障模拟中的断流、命中回应后修改请求重试、把候选答案写回 agent 会话分别立项。之前讨论的重试暂存预算属于[后台待办](../TODO.md#retry-with-modified-request)。

以下是本稿的**推荐值，供审阅**。后文按这些推荐值展开。

| 决定 | 本稿推荐 | 决定的实际影响 |
|---|---|---|
| 阻断的含义 | 动作名用 `Block`，返回协议原生错误 | 客户端能识别调用已结束；不需要等待网络超时 |
| 多条规则命中 | 阶段内按顺序执行，Rewrite 继续，Block 终止 | 可以先脱敏再改参数；顺序会影响结果 |
| 如何保证四种动作都可用 | 完整能力由显式接入的本地转发入口提供；原 hooks 继续支持观察 | 只改插件，可复用监听端口；目标流量需要接入该入口 |
| 等待完整响应超过预算 | 仍可能 Block 时返回规则求值错误；只有 Rewrite 时可放行原回应并记录跳过 | 用户能预见阻断失效或延迟过长时的行为 |
| 关闭录制后的行为 | 规则仍执行，只保留聚合计数，不保存新的正文或逐条 Trace | 规则范围与捕获范围可各自配置 |

### 设计参照

Burp 将人工暂停的 interception rules 与自动替换的 Match and replace 分开；后者支持单条启停、按列表顺序运行、限制在作用域内和内置测试。D-message 借用自动处理的顺序与试跑方式，再加入 LLM 消息块选择器和终止动作。[Burp Match and replace](https://portswigger.net/burp/documentation/desktop/tools/proxy/match-and-replace) · [Burp Proxy settings](https://portswigger.net/burp/documentation/desktop/settings/tools/proxy)

## 2. 用户入口与操作流程

### Rules

- 顶层增加 `Rules`，与 `Trace`、`Repeater` 并列。页内有 `Request`、`Response` 两列规则，窄屏用两个标签切换。各阶段独立排序。
- 列表显示启用状态、名称、范围摘要、动作和命中调用数。支持新建、编辑、复制、停用、删除和上下移动；顺序就是优先级。复制产生独立的停用草稿。
- `Pause rules` 暂停新调用的在线处理。`Record` 继续只控制捕获。离开 Rules 页时，仍可在 Trace 顶栏看到规则是否生效；未配置规则时不占用列表空间。
- 新规则默认是草稿，编辑已发布规则会产生待发布修改。只有 `Enable`、`Publish changes`、停用、删除或发布排序才改变生效版本。测试和取消编辑不会改变线上行为。
- 发布前显示客户端、协议、是否需要缓冲、当前接入能力。范围包含无法执行的路径时列出具体客户端和缺少的能力，用户可缩小范围或配置接入。没有验证过的路径不标为受规则保护。

### 从 Trace 建规则

1. 在 Request、Response 或 Full JSON 中选中字段，选择 `Create rule from here…`。默认带入客户端、协议、阶段和当前 Trace，模型默认不限。
2. 来自结构化消息卡时，默认 `Match blocks like this`；来自固定参数时，默认 `Exact JSON path`。编辑器同时展示本条样本的实际路径和将保存的选择方式。
3. 用户选择匹配条件和动作，点击 `Test this rule`。在样本中高亮命中字段；改写显示前后值，阻断显示发生阶段、是否已转发以及将返回的错误。
4. 点击 `Test enabled rules` 可以试跑整条链。编辑中的规则在其拟发布位置参与预览，界面标为 `Including draft`；选 `Published only` 可核对当前生效版本。
5. 发布后只影响新调用。历史 Trace 是测试输入，创建、试跑和发布规则都不会改写它。

**例**：选中 Codex 请求的 `/input/57/output`，插件识别到它是 `build_report` 的工具结果。“同类块”保存工具结果类型及配对工具名；“精确路径”才保存下标 57。如果点中的是最后一个输入项，默认范围是 `Last input item`。如果点中历史项，应提示 `All input items` 会扫描历史，并在保存前展示本次命中数量，避免默认规则连原样本都匹配不到。

## 3. 一条规则的模型

| 字段 | 语义 |
|---|---|
| Name / ID | 名称可修改；内部稳定 ID 用于排序、修订和追溯。同名规则在审计中按 ID 区分。 |
| Scope | 客户端、协议、可选模型，以及必要时的传输限定（JSON / SSE，默认 Any）。每一维可多选，维内取任一，维间全部满足。精确值或显式 `Any`，未知客户端不匹配某个命名客户端。 |
| Stage | `Request` 或 `Response`。响应规则可额外读取已转发请求的元信息，例如模型；动作只作用于当前阶段。 |
| Select | 从当前版本的消息中选出候选对象。由语义块、整份 JSON 或精确 JSON Pointer 表达。 |
| When | 对候选对象运行有类型的条件。无附加条件时明确显示 `Always for selected items`；全范围无条件阻断在发布摘要中突出显示。 |
| Then | 单选 `Rewrite` 或 `Block`。Rewrite 可包含多项补丁；Block 可指定给客户端看的简短原因。 |

元信息的取值时间也属于规则语义。客户端、协议和入站请求的模型在进入时固定，决定哪些请求规则适用。响应阶段的模型筛选使用 D-message **实际转发的请求模型**。只有独立、可靠的证据才能显示最终服务请求的供应商或模型，它们不参与本期的默认范围匹配。

### 3.1 选择对象

| 选择器 | 返回什么 | 典型用途 |
|---|---|---|
| Whole body | 当前阶段的根对象，一个候选 | 检查参数组合、设置顶层预算 |
| Exact JSON path | RFC 6901 JSON Pointer 指向的值 | 匹配 `/max_output_tokens`；数组下标按实际索引解释 |
| Last input item | 字面上的最后一个输入项及选定层级的块 | 区分“最后是用户追问”和“最后是工具结果” |
| All input items | 本次请求承载的全部输入项或内容块 | 扫描明确需要处理的历史内容 |
| Response output | 本次模型输出的项或内容块 | 匹配回答文本、进度消息、原生工具调用 |

- 编辑器允许选择 **item** 或 **content block** 层级，在该层级内检查 role、块类型、文本、工具名、phase 等可用字段。所有条件绑定同一个候选；两个不同块各满足一半条件，不构成 `Match all`。
- Responses 对应 `input` 和 `output`，Messages 对应 `messages` 和回复 `content`，Chat Completions 对应 `messages` 和 `choices[].message`。字符串输入、字符串 content 都映射回原字符串路径。协议原生字段始终能用 JSON Pointer 检查。
- role 取自协议字段或显式标记为派生的显示角色。工具结果可通过同一次调用可见的工具声明调用项与结果 ID 配对，命名空间保留。缺失或歧义时工具名记为未知。文本中长得像角色或工具名的标签只按文本处理。
- 语义选择器产生**真实路径**，包括原生项上没有 `content` 包装的 Responses 调用结果。预览里的扳手标签、经过截断的摘要和美化文本仅用于识别位置，补丁写入原值。
- 同一请求可能重传整段历史。树上推断出的 `This turn` 带有不确定性；默认选择器使用本条请求可以独立确定的边界。从 `Last input item` 取用户消息时，最后一项若是工具结果，就得到零个符合条件的用户项。

### 3.2 条件、类型与多命中

- 支持 `Equals`、`Not equal`、`Exists`、`Missing`，文本另有 `Contains`、`Matches regex`，数值另有大小比较。默认文本区分大小写，可显式关闭。数字 1024 与字符串 `"1024"` 分开；null 是存在的 JSON 值。
- 精确路径缺失可用 `Missing` 判断。缺失值对其他普通比较均为不匹配，包括 `Not equal`。语义选择器没有任何候选时整条规则不命中。
- 条件组支持 `Match all` 和 `Match any`，第一版采用单层组。一个候选符合任意数量的条件都只计一次。正则在发布时编译，使用有执行界限的实现；不支持的语法在字段旁报错。文本替换的替换值默认按字面量解释。
- 默认处理所有符合条件的候选。编辑器显示 `All matches`，可显式改为 `First match`。遍历顺序是协议数组顺序；规则不依赖 JSON 对象键的序号。规则命中数按调用计，详情另显示这次命中了几个对象。

### 3.3 动作

**Rewrite**

1. `Replace text` 在选中的字符串内替换匹配片段。文本查找、正则、是否替换全部出现位置在预览中明确。选择多个块和替换单个字符串内的多处文本是两个不同的维度。
2. `Set value` 可写入命中的值，或另一个明确指定的路径。值按 JSON 类型保存；父对象存在时可设置缺失的对象成员。数组只允许写已有位置或显式追加到 `/-`。
3. `Remove` 删除命中的字段或块。按一次规则开始时的快照解析具体路径。批量删除同一数组时从后向前处理；重复目标去重，互相覆盖的父子目标及不兼容写入报错。固定目标即使被多个候选选中也只执行一次。
4. 每条规则的补丁原子应用，在临时副本上验证类型、必填字段、协议形状、配对关系及输出格式。成功后才能成为下一条规则的输入。实际计算出的相同值记录为 `Matched · No change`。协议判定为受保护或无法一致重建的字段在编辑器中标出原因，例如仅改正文中的流模式却会破坏客户端协商、或试图重写签名内容。

**Block**

任意候选命中即停止该阶段，不向下一跳发送被阻断的正文。建议默认 HTTP 403，稳定内部码为 `rule_blocked`；客户端收到其协议可解析的错误信封和可配置的公开原因。协议没有独立错误码位置时保留原生错误结构，在 Trace 中记内部码。规则 ID、样本正文和调试详情留在本地。请求阶段 Block 不再进入响应规则。响应阶段 Block 保留上游已产生响应及可能计费的事实。

### 3.4 可审阅的配置示例

下面的 JSON 表示一版规则集。两个数组的顺序即执行顺序。`target: "body"` 指当前阶段的根对象；`target: "match"` 指选中的原生字段。名称和内部表达用于评审，界面通过表单生成配置。

```json
{
  "schemaVersion": 1,
  "request": [
    {
      "id": "short-answer-budget",
      "name": "Limit short answers",
      "enabled": true,
      "scope": { "clients": ["codex"], "protocols": ["responses"], "models": "any" },
      "select": { "from": "lastInputItem", "level": "contentBlock", "take": "all" },
      "when": { "all": [
        { "field": "role", "op": "equals", "value": "user" },
        { "field": "text", "op": "contains", "value": "简短回答" }
      ] },
      "then": { "action": "rewrite", "ops": [
        { "op": "set", "target": "body", "path": "/max_output_tokens", "value": 1024 }
      ] }
    }
  ],
  "response": [
    {
      "id": "withhold-draft",
      "name": "Block draft answers",
      "enabled": true,
      "scope": { "clients": ["codex"], "protocols": ["responses"], "models": "any" },
      "select": { "from": "responseOutput", "level": "contentBlock", "take": "all" },
      "when": { "all": [
        { "field": "type", "op": "equals", "value": "output_text" },
        { "field": "text", "op": "contains", "value": "Internal draft" }
      ] },
      "then": { "action": "block", "reason": "Draft response withheld" }
    }
  ]
}
```

对于一条预算为 4096、最后一个用户输入块含“简短回答”的请求，Trace 应显示 `4096 → 1024`。若上游正文含 `Internal draft`，同一条 Trace 再显示 `Response blocked`、上游原始回应和发给 agent 的错误。两条规则各命中一次，D-message 只发起一次上游调用。

另外两个动作可以用同一份报告样本审阅：

- **Request / Block**：最后一个输入项是工具结果，按调用 ID 配对到 `build_report`，结果含 `DRAFT_ONLY`。阻断整条请求，公开原因为 `Draft report`。若该工具结果仅存在于前几轮，当前最后一项是新的用户消息，则放行。
- **Response / Rewrite**：选择本次回复的文本块，把 `/workspace/demo/report.md` 中的 `/workspace/demo/` 替换为空字符串。agent 收到 `report.md`。若第二条规则在同一阶段检查原路径前缀，它读取的是已经缩短的文本；整链试跑应呈现这一差别。

## 4. 在线执行与一致性

1. **进入**：为每条入站调用分配独立 ID，取得当时已发布的不可变规则集版本及可信路由信息。session ID 只用于归组。并发请求和客户端重试各有自己的调用 ID。
2. **请求阶段**：记录入口快照，按顺序检查范围、选择对象、判断条件并执行。应用后的值供下一条读取；每条规则最多运行一遍。遇到 Block 即生成客户端错误，否则将最终请求转发一次。
3. **响应阶段**：使用同一规则集。先按客户端、协议和已转发请求筛出可能适用的规则。没有候选则正常交付；有候选则按第 5 节决定是否缓冲，在上游回应的工作副本上按序处理。
4. **提交**：一旦开始向客户端提交状态或有意义的正文，记录提交点。需要改变状态或完整丢弃正文的决策必须在提交之前作出。最终只交付选定回应或协议错误。
5. **结束**：记录已知的上游状态、动作结果、下游写出状态和耗时。写完响应说明服务已发出；agent 是否解析、显示或执行工具，属于另一层事实。

两阶段各有自己的有序列表。用户同时编辑、重排或停用时，发布使用版本号做乐观并发检查，冲突一方看到 `Rules changed · Reload`，不会默默覆盖另一份编辑。一次发布完整切换；在途请求继续使用进入时的版本。两个请求可以属于同一会话并使用不同版本，Trace 各自注明。

## 5. 流式响应、超时与错误

### 5.1 流式语义

下表是**调试转发入口的交付目标**，当前版本还没有这些在线规则。每一格按实际协议和路由验收。

| 操作 | JSON 回应 | SSE 回应 |
|---|---|---|
| Request / Rewrite 或 Block | 解析入站请求后即可执行 | 同左，客户端要求 stream 不影响请求匹配 |
| Response / Block | 检查一次完整正文，阻断时发原生错误 | 先缓冲并识别终结事件，决策前不发任何正文或工具事件 |
| Response / Rewrite 文本 | 在原生 JSON 中替换匹配的字符串 | 第一期目标是三种协议的普通回答文本；同步相关增量、完成事件和快照 |
| Response / Rewrite 结构 | 设置或删除可写字段并校验最终协议结构 | 任意结构重排、签名/密文修改不列为第一期支持；在编写规则时显示能力差异 |

能兼容 JSON 和 SSE 的规则可选 `Any transport`。依赖只支持 JSON 的结构改写时，编辑器要求范围显式限定到 `JSON only`；不允许对流式调用显示“规则已启用且可以生效”。

请求规则的传输条件看入站请求要求的模式。响应规则以实际收到的 Content-Type 和协议帧为准；仅凭请求中的 `stream` 不能排除一份以 JSON 返回的上游错误。对响应格式的判断发生在向 agent 提交之前。

- 单纯请求改写在上游调用前完成。录制本身及不在响应规则范围内的流量继续实时转发。
- 对需要检查完整输出的 SSE，编辑器标注 `Buffers response`，并列出涉及的客户端。数据帧边界可能切开匹配字符串，先按协议解析出完整逻辑块，再执行与普通 JSON 相同的匹配。待决定期间保留上游状态、顺序和事件；如果仍可能改变 HTTP 状态，客户端侧暂不提交 200 或 SSE 注释。
- 未改动时从缓存按顺序释放原事件。改动时，适配器须保持事件序列、ID、工具配对、终结信号和最终快照一致。Responses 要同步文本 delta、item 完成和终结快照；Anthropic Messages 要保持 block 索引及 start/delta/stop 对应；Chat Completions 要保持 choice 索引、finish reason 和终结帧。保留未涉及的原生内容；usage 表示上游实际消耗。
- 流式支持按“协议 × 可编辑字段”公布。适配器只能可靠重写文本时，编辑器只对此组合开放文本改写；经过验证的整条响应阻断仍可开放。新类型事件、无法解析的编码或缺失终结事件，都不能据此声称完整检测通过。加密块只展示类型和有无；第一期不解析密文含义。
- 保留原协议和客户端需要的调用标识。本期负责本次交换；供应商保存的历史或后续引用 `previous_response_id` 的上下文可能仍含原回应。对于需要“以后每轮也采用新历史”的场景，能力说明中单列这一限制。

### 5.2 建议故障策略

| 情况 | 客户端处理 | Trace 结果 |
|---|---|---|
| 路径缺失且规则没有要求写该路径 / 条件不满足 | 继续下一条 | No match，仅在试跑详情展开 |
| 已命中但补丁无效、改写后协议无效 | 撤销本条修改；建议返回原生规则执行错误，避免发送半成品 | Rule error，给出规则与路径 |
| 上游正常返回其自身错误 | 保留上游错误类型、状态与正文；显式选择该错误正文的规则才参与改写 | Upstream error，与 Block 区分 |
| 等待或缓存超限，仍有可能阻断 | 在提交前结束，以原生错误告知求值超时或资源不足 | Timed out / Buffer limit；不计为 Block 命中 |
| 等待或缓存超限，候选仅含 Rewrite | 建议发布摘要显示 `On limit: pass original response`；释放已缓存原始前缀并接续原流，放弃本阶段改写 | Rewrite skipped，显示原因 |
| 上游截断或客户端取消 | 随客户端取消停止上游工作；记录截断或取消，保留已提交事实 | Upstream incomplete / Client disconnected |
| 写回开始后发生错误 | 使用该协议允许的流内错误或结束流；不再尝试返回第二个 HTTP 状态 | Delivery interrupted，区分部分提交 |

**预算建议，待压测**：第一版单条待判断响应最多缓冲 8 MiB、60 秒，进程的聚合缓冲上限建议 64 MiB。全局容量不足时立即走上表对应策略。时间从开始等待上游响应计算，包含等待首包。允许调试入口按请求控制 Bun 的空闲计时，同时以独立截止时间和取消信号控制资源。客户端、上游及中间代理的截止时间仍可能更短。展示截断的 Trace 样本不能得出“完整正文未命中”。[本机测试记录](../TODO.md#retry-with-modified-request)

建议把可预期的失败做成固定映射，方便协议适配和 UI 共用测试：主动 Block 为 `403 / rule_blocked`，本地执行错误为 `500 / rule_evaluation_error`，等待超时且必须结束为 `504 / rule_evaluation_timeout`，缓存容量不足且必须结束为 `503 / rule_buffer_limit`。HTTP 头已提交后只记录内部码，并按协议结束已有响应。上游自身的 403 或 500 继续标来源为上游。

## 6. 接入方式及能力声明

**推荐实现**：在插件现有本地服务增加可选的模型转发路由，客户端显式接入；该路由持有入站请求和返回通道，作为完整规则的唯一执行者。沿用 Magpie 做模型路由和鉴权。管理页面和调试路由可共享监听端口，分开认证、路径和错误信封。单纯安装插件或打开 Rules 页，不会自动将现有客户端流量改道。

| 接入方式 | 能力依据 | 产品表现 |
|---|---|---|
| 现有 Bun gateway hooks | 请求 hook 可返回部分字段修改；改动 model、stream 或受保护工具字段会回滚。响应 hook 是完成后的异步观察 | 保留现有录制。若后续开放有限请求改写，应列出许可字段；不在此路径承诺完整 Block 或回应改写 |
| Magpie 同步 middleware | 普通路由支持请求改写或拒绝，且有完整 JSON 或单个 SSE 事件回调。响应 writer 可先提交状态；Codex 自身登录直通分支跳过 middleware | 可作为将来按能力启用的执行方式。不能仅凭看见 `/backend-api/codex/responses` 就判定全部动作可用 |
| D-message 调试转发入口 | 插件决定何时向上游发送、何时向客户端提交 | 验证通过的协议、路由和字段开放四种行为；未验证组合在发布前显示 `Unsupported on this route` |

依据：[Magpie 请求/响应 hooks](https://github.com/yetone/magpie/blob/v0.1.4520/docs/subsystems/gateway-request-hooks.md) · [middleware writer](https://github.com/yetone/magpie/blob/v0.1.4520/internal/middleware/run.go#L291-L331) · [Codex 托管和直通分支](https://github.com/yetone/magpie/blob/v0.1.4520/internal/gateway/codex_backend.go#L284-L354)

**接入契约**

- 仅将显式配置的本地模型路径转发到固定 Magpie 上游。分别验证 Responses、Anthropic Messages、Chat Completions，以及 Codex 实际使用的 backend Responses 路径。验证包括鉴权、客户端识别、取消、模型协议和下一轮工具关联。某个客户端不能配置此入口时，其原路径继续显示实际能力。
- 命名客户端的 Scope 必须来自可信接入绑定或宿主上下文。JSON 正文里的名字、session ID 以及一段看似相同的 prompt 都不能证明客户端身份。涉及原生登录时验证允许透传的认证和协议头；不保存令牌、Cookie 或页面凭据。
- 调试入口负责自己接入的调用的录制和执行。若 hooks 无法取得跨入口的一致调用 ID，推荐按显式的客户端绑定划分唯一录制入口：迁入的客户端由转发入口录制，其他客户端仍走 hooks。界面注明该绑定绕过调试入口的流量不在其覆盖范围。需要同时混用两个入口时，先验证稳定来源标识；不能按时间或 session 猜测两条记录相同。
- Repeater 和历史试跑默认绕过在线规则，避免相同请求补丁被二次应用。所有路径都不自动触发第二次推理。

## 7. Trace 如何记账与展示

### 一次调用的四个观察点

| 字段 | 内容与可用条件 |
|---|---|
| Request / Received | D-message 收到的原生请求，作为请求侧不可变基线 |
| Request / Forwarded | D-message 实际转发给 Magpie 的版本；请求 Block 时为 `Not sent`。Magpie 内部进一步转换出的供应商载荷不冒充此字段 |
| Response / Received | D-message 从上游收到的版本、状态和完整性；没有发出请求时为 `Not called` |
| Response / Sent to client | 实际发出的结果，包括改写正文或本地规则错误；断开时区分尚未写出、部分写出、写完 |

- **列表与树**：沿用现有客户端、消息摘要、工具名、最终答复及活跃分支。只在有干预时显示 `Request rewritten`、`Response rewritten`、`Request blocked`、`Response blocked`。同一调用两个阶段都发生变化时保留两个标记；不拆成两条记录、不插入伪会话节点。
- **详情**：有变化的一侧增加 `Received / Forwarded / Diff` 或 `Received / Sent to client / Diff`。默认请求看实际转发版本，响应看发给客户端的版本。Request blocked 时默认展示被挡住的请求。Diff 使用原生字段路径；按规则展开能看到各自修改，最终 diff 展示净效果。
- **规则轨迹**：按阶段和执行顺序展示名称、规则 ID、修订号、命中对象数、实际路径、动作结果、耗时。线上默认省略未命中规则；试跑可以展开每一条。历史规则被改名或删除后，旧记录仍显示当时生效的版本。
- **搜索**：保留 `request:`、`response:`、`tool:` 及原有排序。存在前后两个版本时同时搜索，结果标出侧和版本并跳转到对应 JSON Pointer；相同版本只搜一次。增加 `rule:`（规则名或稳定 ID）和 `action:`（如 `request.block`）以定位实际干预。命中原始回应时明确标注该内容是否被发出。
- **状态与计数**：调用的上游状态、规则结果、交付状态分开保存。模型返回 200 而响应被 Block，要能在同一页看到上游 200 和客户端 403。`Hits` 为命中调用数，`Applied` 为实际改写或阻断数；试跑、同一规则命中多个块、无变化替换都不能虚增实际干预数。
- **兼容**：历史 hook 记录按其原有采集点展示。缺少精确转发快照、状态码或原生 SSE 帧时标 `Not recorded`，不能用原请求复制出一个看似确定的转发结果。会话树继续根据捕获的入站请求推断；规则改写不会改变原有分支归属。

### 与已有 Repeater 的接口

有真实转发快照时，`Send to Repeater` 默认以它为来源，同时允许选择入口原版。Request blocked 时以入口原版作为草稿。草稿固定来源版本，已有 `Changes` 一直比较此次打开的请求基线。现有标签恢复、撤销、并发队列和独立运行记录继续使用原有流程。规则页面的 `Test` 不创建 Repeater run。

## 8. 试跑、存储和实现拆分

### 试跑可信度

单条试跑与整链试跑使用和在线相同的选择器、匹配器、执行器及验证器，不调用真实上游。在样本缺失时显示 `Insufficient capture`，指出缺的是请求字段、上游回应、路由信息或完整流。

对整链试跑还有一个重要区别：请求在预览中改写以后，系统可以继续用样本里**曾经收到的回应**测试响应规则，但无法预测修改后的请求实际上会让模型回答什么。这里显示 `Using recorded response`。若请求已被 Block，响应列显示 `Not reached`。相同输入与规则版本应得出相同的命中路径、顺序和补丁。

### 逻辑数据与并发

| 数据 | 建议保存方式 |
|---|---|
| 规则与发布版本 | SQLite 保存草稿、不可变发布快照、当前版本指针和每个阶段的有序 ID。同一事务写入完整快照并切换指针。请求处理读取内存中的对应版本，避免逐块查库 |
| 调用与版本差异 | 延用 `calls` 主记录、调用 ID 和现有请求/回应接口。新增关联表存采集入口、规则集版本、完整性、实际传输状态及不同的快照或可重建补丁。相同内容只存一次 |
| 每条规则执行记录 | 键包含调用 ID、阶段、执行序号；记录规则版本、路径与变更或终止原因。与最终调用状态一起结算，重复完成回调幂等 |
| 全局计数 | 允许按版本聚合。未录制的调用只更新计数；不把命中片段、错误中的正文或请求 ID 偷渡到持久日志 |

- 增量迁移，新列和关联记录可空；旧版读图、MCP 查询和已保存草稿仍有定义明确的原始来源。新 Repeater 标签的来源键包含请求快照版本，避免从 Received 与 Forwarded 打开的草稿互相覆盖。
- 规则编辑、读取调用、试跑及发布使用现有本地页面认证。读取当前配置带修订号，写操作携带预期修订号。发布校验失败时保留上次有效版本。暂停状态随重启恢复。
- 停止录制允许此前已开始录制的调用完成。清除历史同时清除关联差异和命中轨迹，保留规则配置；迟到回调不能复活已删除记录。中途进程退出时，未结算记录标记交付未确认；不会为了补写 Trace 重发调用。
- 实现顺序建议为 **纯规则引擎与样本 → Rules 编辑及试跑 → 明确接入的在线执行 → Trace 端到端验收**。从[现有 JSON Pointer 与编辑逻辑](../trace-api.js)中提取无存储副作用的补丁部分；参考[原生协议适配](../ui/protocols.js)、[工具关联](../ui/response-items.js)和[已有差异视图](../request-diff.js)。在线修改始终指回原生字段，不能把为展示生成的消息卡序列化为真实请求。

## 9. 发布前验收

使用本地可控上游和模拟 agent 记录实际 HTTP 请求数、状态、正文及 SSE 事件。至少为三个公开协议各跑 JSON 和 SSE 用例；Codex backend 路径单独验接入。模型上游收到什么、客户端实际读到什么应作为断言，不能只断言页面文字。

| 用例 | 必须观察到的结果 |
|---|---|
| 请求 Rewrite 与未命中对照 | 命中时上游只收到一份已改请求；未命中时原始正文通过；客户端每次都只有一份结果 |
| 响应 Rewrite | 普通 JSON 中只改目标字段；SSE 中匹配词跨两个 delta 也能改，终结快照一致；未改动的工具 ID 在下一轮仍可配对 |
| 两种 Block | 请求 Block 时上游计数为 0；响应 Block 时已转发一次，客户端只收到规则错误，连被挡住的第一个正文块也收不到 |
| 顺序与多命中 | 第二条可命中第一条改出的值；反向排序产生预期差异；第三条在 Block 后不执行；重复候选不会重复写固定字段 |
| 选择器与协议边界 | 多轮重传不会误触 Last input item；数字、字符串、null、缺失分开；配对失败工具名未知；多个 choice、混合块、纯文本输入和空输出均可解释 |
| 两个阶段同一 Trace | 显示请求改写和回应阻断的两个动作；上游与下游状态有据可查，点击 `rule:` 结果可定位到对应步骤 |
| 修订、暂停与并发 | 同一 session 并发两次调用不会串轨迹；一次调用中途发布新版本，两阶段仍引用同一旧版本；新调用使用新版本 |
| 预算与错误 | 超时、容量耗尽、无效补丁、截断及断连有各自原因；有可能 Block 的内容不因缓冲溢出而泄出；已部分交付绝不记为整条已挡住 |
| 历史试跑与录制关闭 | 试跑不联网、不产生 Run、不计线上命中；关闭录制后规则仍生效且不新增正文；旧 Trace 缺少数据有明确提示 |
| 来源与兼容 | 同一次调试调用只产生一条 Trace；绕过执行入口的流量不标成已检查；旧标签、指定来源版本的 Diff、历史清除与重启恢复通过 |

**评审通过条件**：先确认第 1 节的五项决定，再确认流式能力表及故障策略。实现后，只有通过上述端到端用例的路由与动作组合才能在界面标为可用。
